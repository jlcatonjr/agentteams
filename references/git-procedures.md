# Git Operating Procedures — AgentTeamsModule

**Canonical reference for all git operations performed by agents or via operator command in this repository.**

Route git operations through `@git-operations`. This document is the authority for command selection, ordering, and recovery strategy.

---

## Category A — Commit and Push

### A.1 Pre-Commit Checklist

Before staging any changes, verify:

1. Tests pass: `python -m pytest tests/ -q`
2. No absolute filesystem paths in staged content (OPSEC — see `@security` trigger list)
3. Docs build checked if `docs_src/` or `mkdocs.yml` was modified: `mkdocs build --strict --site-dir _site` (CI builds the same way; `_site/` is gitignored)
4. No backup files (`.bak`, `.bak[0-9]`) or `__pycache__` staged
5. If any CLI flag or help string changed: `python -m agentteams.man > agentteams.1`. CI
   diff-checks the man page and no local test does, so a help-text edit made after the last
   regeneration fails CI (PR #101, 2026-10-04).
6. If an integrity-pinned module changed (`agentteams/integrity.py` ENFORCEMENT_MODULES): after
   `@security` review, `agentteams --write-integrity-manifest` and review the diff. Re-pin after
   *every* later edit to a pinned module, including message-only edits.

If any check fails, resolve before staging.

### A.2 Staging

Stage only relevant files — never use `git add .` blindly:

```bash
# Stage specific files
git add <file1> <file2>

# Stage a directory subtree
git add docs/

# Verify what is staged before committing
git status --short
git diff --cached --stat
```

Files to explicitly **exclude** from staging:
- `tmp/__pycache__/`
- `*.bak`, `*.bak[0-9]*`
- `.DS_Store`, `Thumbs.db`
- `agentteams.egg-info/` (regenerated by pip)
- Any file containing absolute `/Users/` or `/home/` paths

#### A.2.1 Shared-clone protocol (more than one agent session in this repo)

**Incident, 2026-08-07.** A second session ran stage-everything commits while another
session's work was mid-flight. Three commits swept mixed content under unrelated messages:
`dc94d24` ("full 87-target sweep") carries an emitter refactor and five clearance-guard edits;
`18e3d6f` ("regenerate the enforcement-integrity manifest") carries a new module, a docs page
and eleven template edits; `2dd9353` regenerated a fixture and propagated an unresolved
merge-conflict block into four golden files. `git log` will not surface that work by its
messages. Full record: `references/plans/retrieval-remediation-provenance.report.md`.

Consequences worth naming, because they are not obvious at commit time:

- **Half-finished state becomes permanent history.** `dc94d24` captured a module mid-refactor,
  over its size ceiling, with the module it depended on not yet created. That commit cannot build.
- **Revert granularity is destroyed.** Once two sessions' edits share a commit, no `git revert`
  isolates either. Rollback becomes hunk-level archaeology.
- **It defeats the dirty-tree guards.** `scripts/regen_example_snapshots.py` refuses to run on a
  dirty tree precisely so unrelated edits are not baked into goldens. Sweeping commits keep
  cleaning the tree, so the guard never fires.

Before staging, and again immediately before committing:

```bash
git log --oneline -1     # note the SHA
git status --short       # note the file set
# ... stage explicitly, by path ...
git log --oneline -1     # SHA moved? another session committed. Re-inspect before proceeding.
```

- **Stage by explicit path.** `git add -A` / `git add .` in a shared clone stages another
  session's in-progress work by construction. A.2's existing rule says this; the shared-clone
  case is *why* it is not merely stylistic.
- **If the diff contains files outside your stated scope, stop.** Do not absorb them into a
  commit whose message describes something else. Either leave them unstaged or say what they are.
- **The one mechanical backstop** is
  `tests/test_stale_detector.py::test_no_tracked_file_carries_an_unresolved_conflict_triad`,
  which fails the suite if a merge-conflict triad reaches any tracked file. It exists because a
  sweep commit propagated exactly that, with the suite green throughout. It is a content guard,
  not a scope guard — nothing mechanically enforces that a commit's contents match its message.

### A.3 Commit Message Format

Follow Conventional Commits (`<type>(<scope>): <summary>`):

| Type | Use for |
|---|---|
| `feat` | New feature or capability |
| `fix` | Bug fix |
| `docs` | Documentation changes only |
| `refactor` | Code restructuring without behavior change |
| `test` | Test additions or corrections |
| `chore` | Dependency, CI, config, or housekeeping changes |
| `security` | Security hardening or vulnerability remediation |

Rules:
- Summary line ≤ 72 characters
- Use present tense imperative: "add feature" not "added feature"
- If the change is non-trivial, add a body paragraph explaining WHY, not just WHAT
- Reference issue/PR numbers in the footer: `Closes #42`

Example:
```
docs: add feature inventory page; share summary table via snippet

- Add docs_src/api-reference/feature-inventory.md: clean category-based
  inventory of 125 features organized by capability area
- Extract shared summary table to docs_src/assets/feature-summary-table.md
  so Home and Feature Inventory pages stay in sync from one source
- Remove features-by-date.md: date attributions were inferred, not verified
```

### A.4 Push

```bash
# Push to the configured remote tracking branch
git push

# If no upstream is set yet
git push --set-upstream origin <branch-name>

# Confirm remote advanced
git log --oneline -3
git status  # should show "up to date"
```

If push is rejected due to diverged remote:
- **Do NOT use `git push --force`** — use `--force-with-lease` only after understanding what will be overwritten
- Preferred: pull first, resolve any conflicts, then push (see Category B)
- `git push --force-with-lease` is safe only if you authored all commits being replaced and the remote has no new work from others

## Category B — Integrating Changes from Main

### B.1 Pre-Integration Check

Always fetch and inspect before integrating:

```bash
git fetch origin
git status
git log --oneline HEAD..origin/main    # commits on remote not yet local
git log --oneline origin/main..HEAD    # your local commits not yet on remote
```

If `HEAD..origin/main` is empty, your branch is up to date — no action needed.

### B.2 Fast-Forward Pull (No Local Changes)

When local branch has no new commits and remote has new ones:

```bash
git pull --ff-only
```

If `--ff-only` fails, the branches have diverged — use B.3 or B.4.

### B.3 Rebase then Pull (Linear History)

Preferred for feature branches that haven't been shared:

```bash
git fetch origin
git rebase origin/main
```

If conflicts arise during rebase, see B.5. After a clean rebase:

```bash
git push --force-with-lease    # only for unshared branches
```

### B.4 Three-Way Merge (Diverged Branches, Shared History)

When `main` and the working branch both have new commits and the branch has been shared (pushed):

```bash
git fetch origin
git merge origin/main
```

Git will create a merge commit. If there are no conflicts, the merge completes automatically. If conflicts arise, see B.5.

### B.5 Manual Conflict Resolution Protocol

When `git merge` or `git rebase` reports conflicts:

1. **Identify conflicting files:**
   ```bash
   git status --short   # look for "UU" (unmerged)
   git diff --diff-filter=U   # show only conflicting hunks
   ```

2. **Inspect each conflict:**
   ```bash
   git diff <file>    # shows conflict markers in the file
   ```
   Conflict markers:
   ```
   <<<<<<< HEAD         ← your current branch version
   your content
   =======
   their content
   >>>>>>> origin/main  ← incoming branch version
   ```

3. **Resolve each file** by editing to the intended final state — remove all `<<<<<<<`, `=======`, `>>>>>>>` markers.

4. **Stage resolved files:**
   ```bash
   git add <resolved-file>
   ```

5. **Complete the merge or rebase:**
   ```bash
   # For merge
   git merge --continue

   # For rebase
   git rebase --continue
   ```

6. **Abort if needed** (restores pre-merge state):
   ```bash
   git merge --abort
   # or
   git rebase --abort
   ```

7. **Post-resolution verification:**
   ```bash
   python -m pytest tests/ -q
   mkdocs build --strict --site-dir _site   # if docs were affected
   git log --oneline -5   # confirm clean commit history
   ```

### B.6 Post-Integration Verification

After any integration (pull, merge, rebase):

```bash
git log --oneline -5         # verify commit sequence makes sense
git diff HEAD~1 --stat       # sanity-check what changed
python -m pytest tests/ -q   # regression check
```

## Category C — Recovery via git diff and git revert

### C.1 Inspecting Changes with git diff

```bash
# Working tree vs. last commit (unstaged changes)
git diff

# Staged changes vs. last commit (what will be committed)
git diff --cached

# Differences between two commits
git diff <commit-a>..<commit-b>

# Single file across two commits
git diff <commit-a>..<commit-b> -- path/to/file.py

# Summary of what changed (names + line counts only)
git diff --stat <commit-a>..<commit-b>

# Show all changes since the last tagged release
git diff $(git describe --tags --abbrev=0)..HEAD
```

### C.2 Retrieving a File at Any Historical Revision

To read a file as it existed at a past commit **without changing your working tree**:

```bash
git show <commit>:<path/to/file>

# Example: view analyze.py as it was 3 commits ago
git show HEAD~3:agentteams/analyze.py

# Pipe to a pager or file
git show HEAD~3:agentteams/analyze.py > /tmp/analyze_old.py
```

### C.3 Restoring a Single File Without Switching Branches

To restore a specific file to its state at a past commit (overwrites the working-tree copy):

```bash
git checkout <commit> -- path/to/file

# Example: restore a corrupted git-procedures.md from the previous commit
git checkout HEAD~1 -- references/git-procedures.md

# Then stage and commit the restoration
git add references/git-procedures.md
git commit -m "fix: restore git-procedures.md from HEAD~1 (file corrupted)"
```

⚠️ This overwrites the file immediately. Use `git show` first to inspect the version you are restoring.

### C.4 Reverting a Specific Commit (Non-Destructive)

`git revert` creates a **new commit** that undoes a prior commit. It never rewrites history, making it safe on shared branches:

```bash
# Revert a single commit (opens editor for commit message)
git revert <commit-hash>

# Revert without opening an editor
git revert --no-edit <commit-hash>

# Stage revert but don't commit immediately (review before committing)
git revert --no-commit <commit-hash>
git diff --cached   # verify the staged revert is correct
git commit -m "revert: undo <describe what is being reverted>"
```

### C.5 Batch Revert of a Commit Range

To undo a range of commits in a single operation:

```bash
# Revert commits oldest-first without auto-committing each
git revert --no-commit <oldest-commit>..<newest-commit>

# Verify the net diff
git diff --cached --stat

# Commit the combined revert
git commit -m "revert: undo commits <range> — <reason>"
```

### C.6 Stashing Work in Progress

Before a risky operation (merge, rebase, checkout), preserve uncommitted work:

```bash
# Stash all tracked changes (and optionally untracked)
git stash push -m "wip: description of what is being stashed"
git stash push --include-untracked -m "wip: including new files"

# List stashes
git stash list

# Restore the most recent stash
git stash pop

# Restore a specific stash without removing it
git stash apply stash@{2}

# Drop a stash after confirming it is no longer needed
git stash drop stash@{0}
```

### C.7 Locating a Regression Commit (Appendix)

`git bisect` is a binary-search tool for locating the exact commit that introduced a regression. It is a diagnostic tool, not a routine operation:

```bash
# Start a bisect session
git bisect start
git bisect bad                  # current HEAD is broken
git bisect good <known-good-commit>   # last known working commit

# Git checks out a midpoint commit; run tests manually, then:
git bisect good    # if tests pass
git bisect bad     # if tests fail

# Repeat until git identifies the first bad commit.
# Always end the session:
git bisect reset
```

## Quick Reference: Decision Tree

```
Need to push new work?
  → A.1 pre-commit checklist → A.2 stage → A.3 commit message → A.4 push

Need to get changes from main?
  → B.1 fetch + inspect
    → No divergence → B.2 fast-forward pull
    → Your commits only, not shared → B.3 rebase
    → Shared branch with divergence → B.4 three-way merge
      → Conflicts? → B.5 manual resolution

Need to recover something?
  → Just inspect a past version → C.2 git show
  → Restore a single file → C.3 git checkout <commit> -- <path>
  → Undo a commit safely → C.4 git revert
  → Undo a range of commits → C.5 batch revert
  → Preserve WIP before risky op → C.6 git stash
  → Find which commit broke something → C.7 git bisect (appendix)
```

## D. Bridge-Refresh Safety (Cross-Repository)

`agentteams … --bridge-refresh` is **destructive at the target project** — it
unconditionally overwrites `CLAUDE.md`, `.claude/README.md`,
`.claude/agent-team.md`, `.claude/quickstart-snippet.md`, and
`.claude/skills/recall/SKILL.md` (and any legacy flat `.claude/skills/recall.md`, which is
left in place, never deleted). Before any such invocation against an external
project (including the `example-research` and `example-collector` test
teams), the full Pre-Flight in `references/bridge-refresh-safety.md` §II
MUST pass:

1. Inventory existing target entry files.
2. For each present file, confirm an `AGENTTEAMS-BRIDGE:BEGIN` fence is
   present (signals bridge-managed; safe to overwrite). Unfenced files
   contain user content and **must not** be overwritten.
3. Confirm the target's working tree is clean for `CLAUDE.md` and
   `.claude/`.
4. Classify each present file as tracked vs untracked. Untracked files
   have no git safety net; never overwrite.

If any check fails, switch to `--bridge-merge`. The merge mode re-renders
only content inside bridge fences and skips unfenced files with a notice.

Recovery procedure when destruction has occurred: see
`references/bridge-refresh-safety.md` §IV. The recovery primitive is
`git checkout HEAD -- <file>`, which only works for tracked files.

## E. Branch Lifecycle (after a merge, and the weekly sweep)

The full procedure is the emitted `.claude/agents/references/branch-lifecycle.reference.md` (the
same file in `.github/agents/references/` and `.codex/agents/references/`). Since the move to `dev`
(§G), feature branches merge locally with `--no-ff`, so they become ancestors of `main` at the next
release (**Integrated** until then). Branches from the earlier squash-merged PRs are **Merged-by-PR**.
Use the tool rather than ancestry by hand:

```bash
agentteams --branch-inventory --branch-report tmp/by-week/<week>/branch-audit   # read-only
agentteams --branch-cleanup tmp/by-week/<week>/branch-audit/branch-deletion-plan.json      # dry run
# @security records PASS for action branch-cleanup:<plan sha256> (printed above). This repo
# enforces signed decisions, so the operator authenticates it with a one-use waiver instead
# (branch-lifecycle reference §4, "When the workspace enforces signed decisions"). Then:
agentteams --branch-cleanup tmp/by-week/<week>/branch-audit/branch-deletion-plan.json --apply
```

GitHub's `delete_branch_on_merge` is **on** for this repository, so a merged PR's remote head is
normally already gone; the local copy is what the sweep removes. A local `--no-ff` merge is
followed by `agentteams --branch-post-merge <branch>` (`--apply` needs an operator `branch-delete`
grant). Deletions are recorded in `references/branch-deletions.log.csv`.

## F. Shared Checkout (operator rule, 2026-10-07)

The repository's main local checkout is an **editable install**: other repositories' `agentteams` runs import
it. Whatever branch and uncommitted edits it holds are what their renders execute. That is how CA-033 picked up
unrecorded agentteams code.

- **Keep the shared checkout on `main`.** Do branch work in your own worktree, then remove it:

  ```bash
  git fetch origin
  git worktree add --no-track ../agentteams-wt/<topic> -b <branch> origin/dev   # origin/main only for a hotfix (§G)
  # ... work, commit, run the local gate, merge into dev (§G) ...
  git push origin <branch>                                                     # no -u (see below)
  git worktree remove ../agentteams-wt/<topic>
  ```

- **Sandboxed agents (Claude Code):** worktrees go under `../agentteams-wt/`, which the project sandbox lists as a
  *literal* writable path. A wildcard entry such as `agentteams-wt-*` makes only the directory itself writable, not
  its contents, so checkout fails there. `.git/config` is write-protected in the sandbox, so use `--no-track` and push
  without `-u`; anything that writes upstream tracking fails with `could not lock config file`.

- **Never run `git reset --hard`, `git checkout -- .` or `git clean -fd` in the shared checkout.** They discard
  other people's uncommitted or untracked work. To update it, use `git switch main` and `git pull --ff-only`,
  which carry unrelated uncommitted changes across.
- **Never run `git worktree prune` in the shared checkout.** It deletes the record of every worktree whose
  directory is missing, including other sessions' worktrees. Remove your own with `git worktree remove <path>`,
  and delete only your own stale record under `.git/worktrees/<name>` (after checking its `gitdir` names your
  path) when its directory is already gone.
- **Before you leave the shared checkout, run `git status`** and account for every untracked file. Untracked
  files follow branch switches, and editable installs would render them. Local registers and logs belong in
  `.gitignore`, not as stray files.
- **Merging a PR doesn't need the shared checkout** (`gh pr merge`). Resolve a conflict in a fresh worktree.
- **One writer per checkout.** A generate or `--update` (including `--self`) holds a lock in the checkout's git
  directory while it writes. A second run that hits it refuses before writing anything and names the holder (pid,
  invoker, start time, flags). Wait for it rather than retrying in a loop. Every locked generate/`--update` run is listed in
  `.git/agentteams-update-runs.log.csv` (a worktree's is under `.git/worktrees/<name>/`), with its invoker, flags
  and exit code. Unlocked runs are not listed: bridge, interop, convert, `--sync`, `--stale-remediate` and
  `--add-fence-markers` runs, and the other standalone commands listed on the `update_lock` API page
  (`docs_src/api-reference/update-lock.md`).

## G. Integration Branch `dev` (operator decision, 2026-11-04)

agentteams uses the **integration-branch model** (brief `git_workflow.branch_model: "integration"`; the generated
`references/integration-branch.reference.md` is the team-wide procedure). GitHub Actions cost follows the number of
CI runs, so `main` advances only at **release milestones**. Rationale and numbers:
`references/plans/ci-cost-branching-strategy.report.md` (local).

| Branch | Advances by | Cloud CI |
|---|---|---|
| `feat/*`, `fix/*`, `docs/*`, `chore/*` | your commits | none |
| `dev` | local `--no-ff` merge after the local gate; invited contributors' fork PRs; automation PRs (vulnscan fixes) | none on push; PR CI for those PRs |
| `main` | the release PR `dev` → `main` (merge commit), or a hotfix PR | full matrix on the PR; Linux-only re-run and deploy on the merge push |

**Local gate** (before every merge into `dev`):

```bash
python -m pytest tests/ -q
mkdocs build --strict --site-dir _site && python scripts/check_docs_site.py pages _site
python -m agentteams.man | diff - agentteams.1
bash scripts/check-durable-tmp-refs.sh
```

**Merge into `dev`:** a worktree on `dev` (`git worktree add ../agentteams-wt/dev dev` once), then
`git pull --ff-only && git merge --no-ff <branch> && git push origin dev`. Never in the shared checkout, which stays on
`main` so editable installs render released code.

**Release** (at a milestone): open the PR `dev` → `main` with the first-parent merge list
(`git log --first-parent --merges --format='- %s' origin/main..origin/dev`). Fix failures on `dev`. If the release renames a CI job that
`main` requires, switch the required checks first (§I). Merge with a
**merge commit**, never squash or rebase. Verify CI and the Pages deploy, then `git merge --ff-only origin/main` on `dev`.

`dev` must be a **protected branch** (no deletion, no force push; no required checks or reviews, so local merges
still push). With `delete_branch_on_merge` on, GitHub deletes a release PR's head branch when it merges, and only
protection exempts it: release #398 (2026-11-07) deleted an unprotected `dev`, which was recreated at `main`.

**Hotfix:** `hotfix/<topic>` from `origin/main`, then a PR to `main`, then merge it. Straight after,
`git switch dev && git merge origin/main && git push origin dev`.

**Branch tools:** `agentteams --branch-inventory` reads `dev` from the brief: `dev` is *integration* (never deleted)
and a branch merged only into `dev` is *integrated* (kept until the release).

## H. Scripted Steps and Operator Handoffs (2026-11-04)

Two failures on one day led to this section. A `cd` into a removed clone failed, and the commands after it ran a trial merge in the shared checkout. Separately, a handoff ran `gh pr merge` straight after a failed check watch, which landed a PR with red CI.

- **Stop on the first failure.** Begin every multi-command step with `set -euo pipefail` and use absolute paths. Don't join dependent commands with `;`. Before writing, confirm you are where you think you are (`git branch --show-current`, or `pwd`).
- **Mind the negated-grep trap.** Under `pipefail`, a guard like `! cmd | grep -q x` can pass falsely, because `grep -q` exits early and `cmd` gets SIGPIPE. Capture the output first, then test it.
- **Gate every PR merge on its checks with `&&`** (release and hotfix PRs into `main`; §G). A checks command only protects a merge that is chained to it. Checks may not have started yet, and `gh pr checks` treats "no checks reported" as a failure, so wait for them first. Pin the merge to the commit that was checked:

  ```bash
  until [ -n "$(gh pr checks "$PR" 2>/dev/null)" ]; do sleep 15; done \
  && gh pr checks "$PR" --watch --fail-fast \
  && gh pr merge "$PR" --merge --match-head-commit "$HEAD_SHA" \
  && git pull --ff-only
  ```

  Stop and read the output if a step fails. The `until` loop runs forever if the PR's workflows never start, so interrupt it if no checks appear after a few minutes.
- **Test platform-specific output on every CI platform before pushing.** If a test reads a file that is generated on only one OS, set that platform in the test. When you can't run on the other OS, simulate it by patching `sys.platform`, and treat a pass as evidence, not proof: the CI job is the real test.

## I. Release PRs That Rename Required Checks (2026-11-13)

`main` requires named status checks (classic branch protection). A release PR that renames one of those jobs cannot
merge, because GitHub waits for a check its workflows no longer produce. Examples: a runner bump
(`test (ubuntu-24.04, 3.11)` → `test (ubuntu-26.04, 3.11)`, #262), a Python version added to the matrix, or a renamed
job. Switch the required set **when the release PR's new checks are green, and not earlier**: until the release
lands, every other PR into `main` runs the old `ci.yml` and would wait forever on the new names.

**Who runs it:** the operator. It needs an admin token and changes what guards `main`. An agent that opens or
watches a release PR checks whether the PR renames a required check. If it does, the agent hands the operator the dry
run's command (§H), and never runs `--apply`.

**How:** `scripts/release_required_checks.py`. It ships with the release, so run it from a checkout of `dev` (the
PR head), not from the shared checkout on `main`:

```bash
python3 scripts/release_required_checks.py --pr <release PR#>              # dry run
python3 scripts/release_required_checks.py --pr <release PR#> --apply <fingerprint>
python3 scripts/release_required_checks.py --restore <backup file it printed>    # shows the restore
python3 scripts/release_required_checks.py --restore <backup file> --apply <fingerprint>
```

- **Proposal:** a required check the PR still produces is kept. A required check it no longer produces is replaced by
  the PR's checks whose names match once version numbers are masked, so `ubuntu-24.04` becomes `ubuntu-26.04`. Nothing
  else changes implicitly. Requiring a new job takes `--add NAME`, and no longer requiring one takes `--drop NAME`.
- **Guards:** the PR is open, targets `main`, and comes from this repository's `dev` (or `hotfix/*`), never a
  fork. Every proposed check is green on the PR head. A required check with no counterpart refuses unless it is
  dropped. The proposal never empties the set. A renamed check keeps the old check's `app_id`, and it refuses if the
  PR's check comes from another app or is a commit status (which any token can post). An `--add` must be a check run
  from an app. `strict` is kept.
- **Apply exactly what was shown:** the dry run prints a fingerprint of the PR head, the current and proposed sets and
  `strict`. `--apply` refuses unless they are unchanged. It saves the previous protection under
  `~/.local/state/agentteams/branch-protection/` and prints the `--restore` command. `--restore` takes only a file in
  that folder, shows the restore, and applies it only with the fingerprint it printed. It refuses an empty set, a
  file whose contents don't match its recorded fingerprint, a backup that would change `strict`, and a `main` that
  has changed since the `--apply`. Every preview lists each check with its app, and flags an unpinned one.
- **Then** merge the release PR (§H's checks-gated merge). If the release is abandoned, restore before any other PR
  into `main` needs to merge.

`--repo owner/name` overrides the repository read from the checkout. Set `GH` to choose the `gh` binary.
