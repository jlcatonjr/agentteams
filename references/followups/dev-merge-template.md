# Follow-up: a built-in integration-merge template for sandbox_handoff

**Status:** open (written 2026-11-15) · **Source:** remediation log line 735 / record 734 (that log, `references/agentteams-remediation-log.csv`, is local and gitignored; its text is quoted below) · **Suggested owner:** @pipeline-core-expert (design), @primary-producer (code), @test-suite-expert, @code-hygiene, @security, @git-operations

## Report

**What is wrong.** Every merge into `dev` from inside the sandbox needs an operator handoff script, and each one is written by hand. Hand-written versions pinned the `origin/dev` tip, so any movement of `dev` while the script waited for the operator invalidated it and cost a new review and `@security` clearance. A shape that survives `dev` moving now exists and has run successfully, but only as hand-written JSON. `agentteams/sandbox_handoff.py` has no way to generate it.

**Evidence.** Remediation record 734, quoted: "followups-close Plan A needed five handoff revisions to land a one-file merge into dev: rev 4 pinned the old origin/dev tip, so when PR #504 moved dev while the cleared script waited, it had to be rewritten and re-cleared. Rev 5 replaced the pinned-tip guard with structural guards (HEAD^1 equals the current origin/dev, HEAD^2 equals the reviewed branch tip, the merge diff is exactly the expected file list) plus a resumable re-merge and a fast-forward-only push; that version survives dev moving without re-review. Proposal: give sandbox_handoff a dev-merge template built this way, so a moving integration branch no longer costs a clearance cycle." Touch points named: `agentteams/sandbox_handoff.py` (dev-merge template); `references/git-procedures.md` section G.

**The reviewed example (local only; described here because the executing agent may not have it).** Spec `leftovers-appendfix.handoff.json` (week 2026-W46, gitignored). It ran OK on 2026-11-15 and pushed merge `f9b8b674` (parents `fd8daa8f`, `4296c64e`) to `dev`. Header: `destructive: true`, `confirm: true`, a `clearance` citing `security-decisions.log.csv`, `requires: [git, python3]`, `touches` listing the new worktree, the new branch and `origin/dev`. Its 10 steps (9 steps + 1 verify):

1. **Scoped process guard.** Checks the SHA-256 of a local guard script, then runs it (`python3 -I`). It blocks only agentteams runs that could write into this checkout.
2. **Fetch and pin guard.** `git fetch -q origin`. The patch file's SHA-256 must equal a literal. `.venv-ci` must import the gate tools at a pinned `cryptography` version.
3. **Resumable worktree, patch and commit.** If the branch already exists, the worktree must be clean and `git diff --name-only B^ B` must equal the exact file list. Otherwise it runs `git worktree add --no-track <wt> -b B origin/dev`, then `git apply --whitespace=error`, `git add` of the named files, and `git commit` (with a co-author trailer), then re-checks the file list.
4. **§G local gate** in a subshell in the worktree. Full pytest with three `--deselect`s: a known failure already on `origin/dev`, and two load-timing tests, which then run alone. Then `mkdocs build --strict`, `scripts/check_docs_site.py pages _site`, the man-page diff, and `scripts/check-durable-tmp-refs.sh`.
5. **Push the branch** (`git push origin B`).
6. **Resumable `--no-ff` merge.** Fetch again. If `HEAD^2` is the branch tip and `HEAD^1` is the current `origin/dev`, it skips. Otherwise `git checkout -q --detach origin/dev` and `git merge --no-ff -m ... B`.
7. **Structural guard.** `HEAD^2` equals the branch tip, `HEAD^1` equals `origin/dev`, `git diff --name-only HEAD^1 HEAD` equals the exact file list, and the targeted tests pass on the merge.
8. **Fast-forward-only push.** `git push origin HEAD:dev`. A plain push is rejected unless it fast-forwards. On rejection the operator re-runs the script, and steps 3 and 6 resume.
9. **Remove the worktree** (`git worktree remove`, no `--force`). The branch is kept (Integrated).
10. **Verify.** Fetch. The branch tip is an ancestor of `origin/dev`, `origin/dev^1..origin/dev` changes exactly the file list, and the worktree is no longer listed.

Plan A rev 5 (`followups-close-a.handoff.json`, local) has the same shape for an already-committed branch. It has no patch step. Instead it pins the branch tip with a literal 40-hex SHA, locally and on origin, and runs a targeted gate the operator chose in a picker.

**What I checked in `sandbox_handoff.py` on origin/dev.** `SPEC_KEYS` = slug, purpose, blocked_by, steps, verify, requires, touches, destructive, clearance, confirm, cwd, plan. Unknown keys are refused. A step is only `{title, run}`. There are **no** `guard` or `resumable` fields. In the example, "Guard" and "resumable" are only title wording plus shell logic. `validate_spec` refuses: a destructive spec without `clearance`; a spec not marked destructive whose commands match `_DESTRUCTIVE_PATTERNS` (`git worktree remove` matches, so this template is always destructive); trust roots; and credential-shaped text. `trust_roots_named` runs `shlex.split` over every `run` string, commit and merge `-m` messages included, and matches `governance_targets.target_is_governance_root` or any `EXTRA_TRUST_ROOT_TOKENS` substring. `write_handoff` renders through `render_script`, which calls `validate_spec`, runs `bash -n` and writes the file atomically with mode 0755. The CLI has `detect`, `write` and `status` subcommands. Tests are in `tests/test_sandbox_handoff.py` (349 lines). The CLI is documented in `docs_src/api-reference/sandbox-handoff.md`. `agentteams.1` does not mention `sandbox_handoff`.

**How this relates to `--merge-pr` (already on origin/dev).** Commits `5c63076d` and `85219cd0` added `agentteams/cli/dev_merge.py`. It defines an operator-signed integration-branch merge authorization, `.agentteams/dev-merge-authorization.json`: Ed25519-signed, a trust root (governance stem `dev-merge-authorization`), ended by a HALT on the `integration-merge` family or on any `dev-merge:` action, with per-merge clearances named `dev-merge:<owner>/<name>:pr-<N>-<head sha>`. While it verifies, `agentteams --merge-pr N` merges pull request N into the integration branch without the gate's merge prompt, but only when `pr_problem` finds nothing: base and head in the signed repository (no forks), base equal to the signed integration branch (never the default branch or a release line), open and not a draft, merge state `CLEAN`, no changes requested, every check and every signed required check passed, every workflow run for the head completed with success, and no governance, agent or workflow path touched. It merges with a merge commit pinned by `--match-head-commit`. So `--merge-pr` is a **PR route**: a GitHub merge of an open PR, gated by green CI and the signed authorization. This item is a **local route**: a `--no-ff` merge made in a worktree and pushed fast-forward-only, through an operator handoff, gated by the local §G gate. The two do not share code. They overlap in purpose for this repository, which is why open question 5 asks whether the PR route makes this template unnecessary here. The local route still matters where no signed authorization exists, where the change touches a path `--merge-pr` refuses, or for generated teams without GitHub CI.

**Known vs not yet known.** Known: the shape works and survives `dev` moving (one real run, plus Plan A rev 5). Not known: whether the shape suits generated teams, since this module ships to every team through `templates/universal/sandbox-handoff.reference.template.md`, whose integration branch, gate and interpreter differ. Also not known: how a resumed run should handle a merge left half-done by a conflict (unverified; the `checkout --detach` in step 6 would probably fail on a conflicted index). And on resume, step 3 checks only the file names of an existing branch commit, not its content.

**Risk of leaving it.** Each merge into `dev` keeps costing hand-written JSON and a fresh clearance whenever `dev` moves. Hand copies drift, for example by dropping the fast-forward-only push or the parent guard. One copy has already pinned the wrong thing.

## Plan

**Preconditions and constraints.**
- Work in a worktree off `origin/dev`: `git worktree add --no-track ../agentteams-wt/integration-merge-template -b feat/handoff-integration-merge-template origin/dev`. Never work in the shared checkout, which stays on `main`.
- Merge into `dev` with `--no-ff`, behind the §G local gate in `references/git-procedures.md`.
- In the Claude Code sandbox an agent cannot add or remove worktrees, commit, or push. Those steps go through an operator handoff, ideally the first one generated by this template.
- Code changes need an `@code-hygiene` audit. This one is security-relevant: it emits destructive scripts and sits next to the trust-root refusal. It therefore needs `@security`.
- **Sequence these items; do not run them in parallel.** Two other open items edit the same file. The agreed lane order is: (1) remediation record 736 (physical line 737), which adds the additional instruction files named in record 736 as trust roots, widening the refusal only; (2) the handoff-trustroot-fp item, the commit-message false positive in `trust_roots_named` (the template's generated `-m` messages pass through that function, so until it lands keep generated messages free of path tokens); (3) this item. Each is rebased on the previous one's merge into `dev`.
- **This item also waits for two gate items.** The timing-budget item replaces the load-timing `--deselect`s with a `perf` marker, deferred by `AGENTTEAMS_PERF=defer` and run separately with `-m perf`. The lineage-regen item removes the known-failure `--deselect`. The template's gate runs the §G gate as it stands when this item lands; `--deselect` is not built in.
- **Which code an agent runs.** The shared checkout is an editable install on `main`, so `python -m agentteams.sandbox_handoff` run from it is main's code. The new subcommand exists there only after a release. Before that, run it from the item's worktree root, and check which copy is imported: `python3 -I -c 'import agentteams;print(agentteams.__file__)'` prints the installed copy (the shared checkout, so main's code); `-I` ignores the current directory, so in the worktree also run it without `-I` from the worktree root and confirm the printed path is inside the worktree.

**Proposed design (for @pipeline-core-expert to confirm).** Name: `integration_merge_spec` and subcommand `integration-merge`, not `dev-merge`, because `dev-merge` is already taken on origin/dev by `agentteams/cli/dev_merge.py`, its signed `dev-merge-authorization` trust root and the `dev-merge:` clearance family. Reusing the name would make clearance rows, HALTs and docs ambiguous between the two routes (a HALT on `dev-merge:` ends the signed authorization, not this template). Add a pure function `integration_merge_spec(*, slug, branch, files, clearance, patch=None, patch_sha256=None, branch_sha=None, commit_message=None, integration="dev", remote="origin", worktree=..., python=None, gate=None, targeted_tests=(), guard_script=None, guard_sha256=None, plan="") -> HandoffSpec`. Add a CLI subcommand `integration-merge` that builds the spec and calls `write_handoff`, for example `python -m agentteams.sandbox_handoff integration-merge --slug S --branch B --files F... (--patch P | --branch-sha SHA) --clearance C [--integration dev] [--python PATH] [--targeted-test PATH]... [--guard-script P --guard-sha256 H] [--emit-json]`. `--emit-json` prints the spec so it can be reviewed or hand-edited before `write`. The output is an ordinary spec: no new `SPEC_KEYS`, no new trust path, and `validate_spec` still decides. Parameters fill the 10 steps above. `files` drives every exact-list guard, sorted and space-joined exactly as git prints them. With `--patch`, the SHA-256 of the patch is computed when the script is written and placed in the script as a literal; with `--branch-sha` the branch tip is the literal. **What stays operator-reviewed:** that literal pin (patch SHA or branch SHA), the file list, and the `clearance` string. If a `--deselect` escape is kept at all, it is an operator-reviewed parameter whose test ids are recorded in the clearance, never a default. **What is no longer pinned:** the `origin/dev` tip. That is the point of the change. **Required on resume:** with `--patch`, step 3 compares `git patch-id --stable` of the existing branch commit with that of the patch and fails on a mismatch; a file-name match alone is not enough. **Clearance bound:** the clearance for a generated script must be use-counted and expiring, or name the generated script's SHA-256 so that the sha pin plus one run is the bound; a re-run after a fast-forward rejection is the same script and the same clearance.
