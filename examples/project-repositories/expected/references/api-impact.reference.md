# API Impact Review Reference — ProjectRepositories

How the team keeps its API and the infrastructure around it current whenever a commit makes a structural
change or adds a feature. A `pre-commit` hook detects the change and updates what can be regenerated
mechanically; the orchestrator's **API Impact Review** sub-protocol then reviews and updates the API
documentation, audits every piece of infrastructure the change touches, and revises it on the findings.
Workflow 11's gate 6b holds the session open until that review is recorded. Tool:
`python -m agentteams.api_impact`.

## 1. What counts as API impact

`python -m agentteams.api_impact detect` compares one diff (the staged index, or one commit) and reports:

| Category | Detected when |
|---|---|
| Modules | a Python module is added, removed or renamed (tests excluded) |
| Symbols | a public module-level function or class, a public method of a public class, or `__all__` is added, removed or re-signed |
| CLI | an `add_argument` option string or an `add_parser` subcommand is added or removed |
| Schemas | a `*.schema.json` file is added, removed or modified |
| Structure | any other tracked file is added, removed or renamed |
| Regenerated | a built-in derived artifact was regenerated by the hook |

Paths under `docs/`, `docs_src/`, `tests/`, `tmp/`, `workSummaries/`, `references/plans/`, `*/expected/`
snapshot trees and the review ledger are left out of every category, and test files wherever they live.
Symbol-level detection reads Python only. Projects in other languages get the module-free categories:
schemas, structure and regenerated artifacts.

## 2. The hook (automatic, never blocking)

`agentteams --update` installs a `pre-commit` hook (opt out with `--no-git-hooks`). On every commit that
stages anything it runs `python3 -P -m agentteams.api_impact --pre-commit`, which:

- prints one line summarizing the staged API impact;
- in the agentteams repository, when the operator has opted in with `git config agentteams.regenerateMan true`,
  regenerates the CLI man page `agentteams.1` from the parser and stages it when `build_team.py`,
  `agentteams/cli/` or `agentteams/man.py` is staged (skipped, with a note, when those paths also hold
  unstaged edits). The opt-in lives in git config, outside the working tree, so files in the tree alone
  never make the hook run the tree's own code.

It reads no brief or project configuration, needs Python 3.11+ (as does the rest of the tool; `-P` keeps the
working tree off `sys.path`), and never changes whether the commit succeeds. A commit made with `--no-verify`, or on a machine without the
hook, is still caught: the review state below is computed from the commits themselves.

## 3. Review state

```
python -m agentteams.api_impact status                    # this branch's commits since its base
python -m agentteams.api_impact status --range A..B       # an explicit range
python -m agentteams.api_impact record --note "<what the review covered and changed>"
```

- **Base.** On a feature branch, the merge-base of `HEAD` with the default branch (`origin/HEAD`,
  `origin/main`, `origin/master`, else a local `main`/`master`). On the default branch itself, the unpushed
  commits (`@{upstream}..HEAD`). `status` prints the range it used. With no resolvable base (no default
  branch, the default branch without an upstream, a detached `HEAD` already on it) it reports **pending**
  (exit 2) and never passes; pass `--range BASE..HEAD` to name the range.
- **Reviewed** means the commit's stable patch-id (`git patch-id --stable`) has a file in the ledger
  `references/api-impact-reviews/<patch-id>.json` **committed at `HEAD`** (an uncommitted record does not
  count). Patch-ids survive rebase and cherry-pick. Merge commits are
  skipped. A squash merge creates a new patch-id, so squashed commits on the default branch show as
  unreviewed.
- **Audit checklist.** For each removed, renamed or re-signed name, `status` lists the tracked files that
  mention it (whole-word `git grep`, the changed file and tests left out, at most 15 files plus the total).
  That list is the scope of the infrastructure audit.
- **`record` is a self-attestation.** It writes one ledger file per unreviewed commit with the note; it
  refuses an empty note. It proves that someone recorded a review, not that the review happened. The
  ledger is committed, so every record is visible in the pull request.

## 4. The review (orchestrator sub-protocol)

1. **Scope.** Run `status`; the impactful, unreviewed commits and their checklists are the scope.
2. **Review and update the API.** With module documentation in the team, `@module-doc-validator` runs its
   Change Impact Analysis on the reported names and `@module-doc-author` updates the API reference, the
   CLI reference and the changelog. Without it, `@technical-validator` reviews the reported names and the
   owning producer updates the API documentation. Project-specific API checks (parity scripts, a project's
   API conformity agent) run here too.
3. **Audit the related infrastructure.** Every file on the checklist, plus the agent docs, references,
   templates, tests and user documentation that describe the changed area: `@conflict-auditor`
   (contradictions), `@adversarial` (assumptions the change broke), `@code-hygiene` (structure and sprawl)
   and `@technical-validator` (examples and references against the code). Re-verify each finding's
   evidence before acting on it (Rule 14).
4. **Revise** through the owning agents (`@agent-updater` for agent documentation), then re-audit what
   changed.
5. **Record.** Commit the revisions first. Then run `record` with a note naming what was reviewed, updated
   and revised, and commit the ledger files on their own (a ledger-only commit is not API impact). Re-run
   `status`: if the revision commit was itself impactful, review it the same way.

A choice only the operator can make goes through the Operator Decision Query. In a non-interactive run
the review runs anyway; when it cannot finish, the session closes as **API review pending**.

## 5. Generated-team notes

- In a repository that does not ignore `tmp/`, nothing here writes there; the only file the review adds is
  the ledger under `references/`.
- The ledger directory is the root `references/` when it exists, else the agent directory's `references/`.
